# RightLingo — Chrome 原生右键菜单翻译插件产品需求文档

## 0. 项目名称与定位

- **产品名称：** RightLingo
- **项目 / 文件夹名称：** `RightLingo`
- **GitHub 仓库名称建议：** `rightlingo` 或 `rightlingo-extension`
- **Chrome Web Store 名称建议：** `RightLingo – Translate in Right-Click Menu`
- **中文描述名：** `RightLingo · 原生右键翻译`
- **一句话定位：** `Translation, right in your context menu.`

RightLingo 的核心差异不是“提供翻译功能”本身，而是尽可能把翻译结果直接呈现在 Chrome 原生右键菜单中，让用户完成“选中文字 → 右键 → 直接阅读译文”的流程，减少弹窗、跳转和额外鼠标移动。

---

## 1. 项目目标

做一个轻量的 Chrome 浏览器扩展，用于快速翻译网页中用户选中的文字。

核心体验是：

> 用户选中文字后，打开 Chrome 原生右键菜单，就能尽可能直接看到译文。

插件不使用网页悬浮窗、不额外弹出气泡，也不替换 Chrome 自带右键菜单。目标是让翻译功能看起来像浏览器原生能力一样，尽量减少额外点击和鼠标移动。

---

## 2. 主要使用场景

这个插件主要不是用于翻译整篇文章，而是处理以下内容：

- 一个单词
- 一个短语
- 一小句话
- 偶尔是一小段文字

典型场景：

- 阅读英文网页时，不认识某个单词
- 看技术文档时，快速理解一个短语
- 阅读活动介绍、邮件网页、论坛内容时，快速翻译一句话
- 不希望复制到翻译网站，也不希望打开额外窗口

因此，产品应该优先优化“短文本翻译”的速度和直接性，而不是追求长文翻译能力。

---

## 3. 核心交互

### 3.1 短文本：直接在一级右键菜单显示译文

用户选中一个单词、短语或短句后，右键菜单直接出现：

```text
译文：标志性的
```

或者：

```text
译文：新加坡本地通讯和活动
```

这种情况下不需要二级菜单。

用户打开右键菜单后，应该能够立即读到翻译结果，不需要继续移动鼠标。

### 3.2 中等长度文本：一级菜单仍尽量完整显示

如果译文稍长，但仍能较好地显示在一个菜单项里，则继续直接显示完整译文。

例如：

```text
译文：此表格用于新加坡当地的通讯和活动。
```

只要一级菜单没有明显过长，就不应该为了形式统一而强制使用二级菜单。

### 3.3 长文本：一级菜单显示摘要，二级菜单显示多行译文

如果译文明显过长，则一级菜单只显示前面一部分：

```text
译文：此表格适用于新加坡当地的通讯和活动…  ▶
```

鼠标移入后，二级菜单展示分行后的译文，例如：

```text
此表格适用于新加坡当地的通讯和活动。
您仍然需要通过官方 NASA Space Apps
活动页面注册才能参加黑客马拉松。
────────────
复制完整译文
```

这样即使用户不展开二级菜单，也能从一级菜单看到译文开头。

---

## 4. 长文本显示规则

二级菜单主要作为长文本的兜底方案。

建议规则：

- 最多显示 10 行译文（默认 5，可在设置里 1–10 调整）
- 每一行作为一个独立菜单项显示
- 超过最大显示范围时，不继续无限展开：一级标题以 `…` 结尾表示被截断，且二级菜单最后一行行末拼接 `…`（不另起一行，仅表示"还有更多"）
- 送翻译的字符数随"二级菜单行数"变化：只翻译够填满菜单的量（约 行数 × 104 源字符，已计入英→中压缩——每行显示 52 格、译文显示宽约为源 0.5，故源字符预算按 2 倍估，确保选 N 行能铺满 N 行），长选文不整段送译，避免响应变慢；原文上限仍 2000 字符（用于存储与"在 Google 翻译中翻译"跳转）
- 预算截断只在词边界处切（`budgetSlice`）：避免把英文单词拦腰切断（如 `after`→`aft` 被逐字翻成"船尾"）。二级行宽上限 52 格是为压在 macOS 系统菜单 ~400px 中间省略阈值以内，否则每行译文会被从中间抠掉一段显示成 `…`
- 菜单里显示的译文通过二级菜单底部的"复制完整译文"获取（点击任意译文行亦可）；长选文只翻译了填满菜单的前缀，故复制的也是这部分，完整原文阅读走"在 Google 翻译中翻译"

- 可以额外提供：

```text
复制完整译文
```

如果完整译文很短，则不显示“复制完整译文”。

---

## 5. 一级菜单的设计原则

一级菜单是整个插件最重要的部分。

优先级应该是：

1. 能直接显示完整译文，就直接显示
2. 能显示大部分译文，就显示大部分
3. 只有确实显示不下时，才启用二级菜单

不要把所有内容都做成：

```text
翻译选中文本 ▶
```

因为这会增加一次鼠标移动，也失去了“右键后马上知道意思”的体验。

推荐文案：

```text
译文：xxx
```

而不是：

```text
翻译：xxx
```

因为此时展示的是已经得到的翻译结果，而不是一个尚未执行的操作。

---

## 6. 点击行为

建议让一级菜单本身同时承担一个简单操作：

> 点击译文 = 复制译文

例如：

```text
译文：标志性的
```

用户点击后，直接把“标志性的”复制到剪贴板。

这样可以避免再增加一个“复制译文”一级菜单项，让右键菜单保持简洁。

对于长文本，可以在二级菜单中提供“复制完整译文”。

---

## 7. 翻译触发时机

为了让用户打开右键菜单时就能看到译文，插件应该尽量在用户完成文字选择之后就提前准备翻译结果，而不是等用户点击右键以后才开始翻译。

用户体验上应该接近：

```text
选中文字
→ 稍等极短时间
→ 右键
→ 译文已经出现在菜单中
```

如果翻译尚未完成，可以临时显示：

```text
正在翻译…
```

翻译完成后，再更新为最终结果。

重点是不要让用户必须先点击“翻译”才能开始处理。

---

## 8. 文本长度判断

不要简单按照固定字符数判断是否需要二级菜单。

原因是：

- 中文字符视觉宽度较大
- 英文字符较窄
- 空格和标点占用宽度不同

实现时可以采用一个近似的“显示宽度”规则。

产品层面只需要满足：

- 短文本尽量留在一级菜单
- 一级菜单不要长到严重影响阅读
- 超出合理范围后自动切换到“一级摘要 + 二级详情”

第一版可以先通过实际测试来调整阈值，不需要追求绝对精确。

---

## 9. 翻译语言

第一版可以先以“外语 → 中文”为主要场景。

建议：

- 自动识别选中文字的语言
- 默认翻译为简体中文
- 中文文本可以不处理，或者后续支持“中文 → 英文”

语言设置可以后续加入插件设置页，不需要第一版就做得很复杂。

---

## 10. 翻译引擎

第一版不要求绑定某一种翻译服务。

可以优先选择：

- Chrome 自带的本地翻译能力（如果当前环境支持）
- 或其他简单、稳定的翻译服务

整个插件最好保留可替换翻译引擎的空间，避免以后更换翻译服务时需要重做 UI 和交互。

用户体验优先级：

1. 响应速度
2. 翻译质量
3. 隐私
4. 成本

由于主要处理的是单词、短语和短句，因此速度比复杂长文翻译能力更重要。

---

## 11. 不做的事情

第一版明确不需要：

- 不做网页悬浮翻译窗口
- 不做鼠标旁边的气泡翻译
- 不替换 Chrome 原生右键菜单
- 不做整页网页翻译
- 不做复杂词典界面
- 不做长文章翻译器
- 不做大量格式化排版
- 不追求完全复刻 Yandex 浏览器的内部 UI

Yandex 的交互方式只是参考，目标是在 Chrome 扩展能力范围内实现相似体验。

## 12. 推荐的最终体验

### 场景 A：单词

用户选中：

```text
iconic
```

右键菜单：

```text
译文：标志性的
```

点击后复制译文。

### 场景 B：短语

用户选中：

```text
local Singapore communications and activities
```

右键菜单：

```text
译文：新加坡本地通讯和活动
```

无需二级菜单。

### 场景 C：短句

用户选中：

```text
This form is for local Singapore communications and activities.
```

右键菜单：

```text
译文：此表格用于新加坡当地的通讯和活动。
```

仍然尽量一级完成。

### 场景 D：一小段文字

一级菜单：

```text
译文：此表格适用于新加坡当地的通讯和活动…  ▶
```

二级菜单：

```text
此表格适用于新加坡当地的通讯和活动。
您仍然需要通过官方 NASA Space Apps
活动页面注册才能参加黑客马拉松。
────────────
复制完整译文
```

### 场景 E：较长文本

一级菜单：

```text
译文：这是一个较长段落的翻译结果开头…  ▶
```

二级菜单：

```text
第 1 行译文
第 2 行译文
第 3 行译文
第 4 行译文
第 5 行译文
第 6 行译文
第 7 行译文
```

## 13. 第一版 MVP 范围

第一版只需要完成以下能力：

1. 用户选中文字后自动准备翻译
2. 右键菜单中出现译文
3. 短文本直接在一级菜单完整显示
4. 长文本自动变成“一级摘要 + 二级多行译文”
5. 二级菜单最多显示 10 行（默认 5，可在设置里 1–10 调整）
6. 超出后显示“复制完整译文”
7. 点击一级译文可以复制结果
8. 默认翻译到简体中文
9. 保持 Chrome 原生右键菜单，不使用网页悬浮窗

完成以上功能后，就已经可以作为一个可实际使用的 MVP。

---

## 14. 后续可选功能

在核心体验稳定以后，再考虑：

- 设置目标语言
- 中英双向翻译
- 自动识别语言
- 复制原文 + 译文
- 查看完整翻译页
- 翻译历史
- 自定义最大显示行数
- 自定义一级菜单最大长度
- 多种翻译引擎切换
- 本地翻译 / 云端翻译切换
- 快捷键触发

这些都不是第一版必须功能。

---

## 15. 验收标准

第一版可以按照下面几条判断是否完成：

- 选中一个英文单词后，右键可以直接看到中文译文
- 选中一句短句后，大多数情况下不需要进入二级菜单
- 选中较长文本后，一级菜单会显示译文开头，并自动出现二级菜单
- 二级菜单中的译文不会无限增长，最多 10 行（默认 5）
- 超出的内容有明确的“复制完整译文”入口
- 点击一级译文可以快速复制
- 整个过程中不出现网页浮窗
- 不破坏 Chrome 自带右键菜单
- 使用体验重点是“少一步操作、尽快看到结果”

---

## 16. 给代码 Agent 的实现建议

实现时请优先保证交互体验，而不是一开始加入大量功能。

建议按以下顺序逐步实现：

1. 先完成“选中文字 → 右键菜单显示固定测试文本”
2. 再接入真实翻译
3. 再实现短文本直接显示
4. 再实现长文本二级菜单
5. 再实现多行拆分和最大行数
6. 再实现复制译文
7. 最后处理翻译速度、缓存、语言识别和异常情况

每一步完成后都先实际在 Chrome 中测试，再进入下一步。

最终目标不是做一个复杂翻译器，而是做一个非常轻、非常快、尽可能像 Chrome 原生功能的“右键即时翻译”工具。
